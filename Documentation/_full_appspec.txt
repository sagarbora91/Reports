[P0052|] विभाग १ — हेतू आणि हा दस्तऐवज कसा वापरायचा
[P0053|Heading 2] Why this document exists
[P0054|] हा दस्तऐवज का अस्तित्वात आहे
[P0055|] Most app projects fail because the specification is written after coding starts, or is written in fragments, or is written so loosely that the developer (human or AI) makes a hundred small assumptions that compound into bugs. The result is a six-month bug-chase where every fix breaks two things. This document exists to prevent that for the Saagar Traders audit app.
[P0056|] बहुतेक अॅप प्रकल्प अपयशी होतात कारण तपशील कोडिंग सुरू झाल्यानंतर लिहिली जाते, किंवा तुकड्या-तुकड्यात लिहिली जाते, किंवा इतकी ढिली असते की डेव्हलपर (माणूस किंवा AI) शेकडो छोटी गृहीतके करतो जी बग्समध्ये जमतात. सहा महिन्यांची बग-शिकार होते जिथे प्रत्येक दुरुस्तीने दोन गोष्टी मोडतात. सागर ट्रेडर्स ऑडिट अॅपसाठी हे टाळण्यासाठी हा दस्तऐवज अस्तित्वात आहे.
[P0057|] The principle: write everything down before coding starts. Every screen. Every button. Every field in every database table. Every calculation. Every error case. Every Marathi translation. Every behaviour when offline. Every cross-reference to the operational Workbook. Once written, this document does not change during the build — if Claude Code thinks a change is needed, the change comes to this document first, gets reviewed, and then gets coded. The document leads, the code follows.
[P0058|] तत्व: कोडिंग सुरू होण्यापूर्वी सर्व काही लिहून ठेवा. प्रत्येक स्क्रीन. प्रत्येक बटण. प्रत्येक डेटाबेस टेबलमधले प्रत्येक क्षेत्र. प्रत्येक गणना. प्रत्येक त्रुटी प्रकरण. प्रत्येक मराठी अनुवाद. ऑफलाइन प्रत्येक वर्तन. कार्यवाहक पुस्तिकेचा प्रत्येक संदर्भ. एकदा लिहिले की हा दस्तऐवज बांधणीदरम्यान बदलत नाही — क्लॉड कोडला बदल हवा वाटला तर बदल आधी या दस्तऐवजात येतो, पुनरावलोकन होते, मग कोड होतो. दस्तऐवज नेतो, कोड अनुसरतो.

[P0075|Heading 1] Section 2 — System Architecture & Technology Stack
[P0076|] विभाग २ — सिस्टम आर्किटेक्चर आणि तंत्रज्ञान
[P0077|Heading 2] Architecture in one paragraph
[P0078|] एका परिच्छेदात आर्किटेक्चर
[P0079|] A Flutter Android application reads and writes to a local SQLite database on each device. Whenever the device has internet, the local database syncs bidirectionally with Firebase Firestore (a cloud database). All three users (Store Manager, GM, Owner) share the same Firestore project. The app works fully offline; data captured offline syncs the next time the device sees the internet. Photos are stored in Firebase Storage (cloud) and cached locally on the device. There is no custom server, no DevOps, no monthly hosting cost.
[P0080|] Flutter Android अॅप्लिकेशन प्रत्येक डिव्हाइसवर लोकल SQLite डेटाबेसमधून वाचतो आणि लिहितो. डिव्हाइसला इंटरनेट असेल तेव्हा लोकल डेटाबेस Firebase Firestore (क्लाउड डेटाबेस) सोबत द्विदिश समक्रमित होतो. तिन्ही वापरकर्ते (स्टोअर मॅनेजर, जीएम, मालक) तोच Firestore प्रकल्प वापरतात. अॅप पूर्णतः ऑफलाइन काम करते; ऑफलाइन घेतलेला डेटा डिव्हाइसला इंटरनेट दिसताच समक्रमित होतो. फोटो Firebase Storage (क्लाउड) मध्ये साठवले जातात आणि डिव्हाइसवर कॅशे केले जातात. कस्टम सर्व्हर नाही, DevOps नाही, मासिक होस्टिंग खर्च नाही.
[P0081|Heading 2] Technology stack — locked
[P0082|] तंत्रज्ञान स्टॅक — पक्के
[P0084|Heading 2] Offline behaviour — the contract
[P0085|] ऑफलाइन वर्तन — करार
[P0086|] The app must be fully usable when offline. Specifically:
[P0087|] ऑफलाइन असताना अॅप पूर्णतः वापरण्यायोग्य असले पाहिजे. विशेषतः:
[P0088|List Paragraph] User can log in offline (PIN check is local against last-known device PIN hash).
[P0089|] वापरकर्ता ऑफलाइन लॉग इन करू शकतो (PIN तपासणी डिव्हाइसवरच्या शेवटच्या-ज्ञात PIN हॅशशी लोकल होते).
[P0090|List Paragraph] User can run a full daily audit offline; data saves to local SQLite.
[P0091|] वापरकर्ता ऑफलाइन पूर्ण दैनंदिन ऑडिट चालवू शकतो; डेटा लोकल SQLite मध्ये जतन होतो.
[P0092|List Paragraph] User can attach photos offline; photos save locally, queued for upload on next connection.
[P0093|] वापरकर्ता ऑफलाइन फोटो जोडू शकतो; फोटो लोकल जतन होतात, पुढच्या कनेक्शनवर अपलोडसाठी रांगेत.
[P0094|List Paragraph] User can create CAPs offline; CAPs save locally, sync on next connection.
[P0095|] वापरकर्ता ऑफलाइन CAP तयार करू शकतो; CAP लोकल जतन होतात, पुढच्या कनेक्शनवर समक्रमित.
[P0096|List Paragraph] User can view PAST audits (those already synced to device) offline. Audits created on OTHER devices that have not yet synced to this device are not visible offline.
[P0097|] वापरकर्ता मागच्या ऑडिट पाहू शकतो (आधीच डिव्हाइसवर समक्रमित झालेल्या) ऑफलाइन. इतर डिव्हाइसवर तयार झालेल्या आणि अजून या डिव्हाइसवर समक्रमित न झालेल्या ऑडिट ऑफलाइन दिसत नाहीत.
[P0098|List Paragraph] When the device reconnects to the internet, sync runs automatically in the background. A small status icon at the top of the screen shows sync state: green dot (synced), amber dot (syncing), red dot (sync failed).
[P0099|] डिव्हाइस इंटरनेटला पुन्हा जोडले की समक्रमण पार्श्वभूमीत आपोआप चालते. स्क्रीनच्या वर एक छोटा स्थिती चिन्ह समक्रमण स्थिती दाखवतो: हिरवा ठिपका (समक्रमित), पिवळा (समक्रमण होत आहे), लाल (समक्रमण अयशस्वी).
[P0100|Heading 2] Conflict resolution — when two devices edit the same thing
[P0101|] संघर्ष निरसन — दोन डिव्हाइस एकच गोष्ट संपादित करतात तेव्हा
[P0102|] It is rare but possible: GM marks a CAP as Verified on her tablet offline, Store Manager marks the same CAP as Done on his phone offline. Both sync later. Rule: last-write-wins by Firestore server timestamp, BUT every write also appends an entry to a CAP audit_log table with the device ID, user ID, and timestamp. So even if a write is overwritten, the history shows both writes and who made each. The app must never silently lose data; it must always show the history.
[P0103|] क्वचित पण शक्य: जीएम तिच्या टॅबलेटवर CAP Verified म्हणून ऑफलाइन खूण करते, स्टोअर मॅनेजर त्याच्या फोनवर तीच CAP Done म्हणून ऑफलाइन खूण करतो. दोघे नंतर समक्रमित होतात. नियम: Firestore सर्व्हर वेळ-शिक्क्यानुसार शेवटचे-लिहिणे-जिंकते, पण प्रत्येक लेखन CAP audit_log टेबलमध्ये डिव्हाइस आयडी, वापरकर्ता आयडी, आणि वेळ-शिक्क्यासह नोंद जोडते. म्हणून लेखन ओव्हरराइट झाले तरी इतिहास दोन्ही लेखने आणि कोणी केली ते दाखवतो. अॅपने डेटा शांतपणे कधीही गमावू नये; इतिहास नेहमी दाखवला पाहिजे.

[P0107|Heading 1] Section 3 — Roles, Permissions & Capabilities Matrix
[P0108|] विभाग ३ — भूमिका, परवानग्या आणि क्षमता मॅट्रिक्स
[P0109|Heading 2] The four roles
[P0110|] चार भूमिका
[P0111|Heading 3] 3.1 — Store Manager (SM)
[P0112|] ३.१ — स्टोअर मॅनेजर
[P0113|] The Store Manager is the primary day-to-day user. The app exists first for the SM. SM logs into the app every evening, runs the daily audit, creates CAPs for Fails, and submits the audit to the GM. The SM also marks Done on CAPs assigned to him as they are completed.
[P0114|] स्टोअर मॅनेजर हा प्राथमिक दैनंदिन वापरकर्ता. अॅप पहिल्यांदा SM साठीच अस्तित्वात आहे. SM दर संध्याकाळी अॅपमध्ये लॉग इन करतो, दैनंदिन ऑडिट चालवतो, नापासांसाठी CAP तयार करतो, आणि ऑडिट जीएमला सादर करतो. SM त्याला नेमलेल्या CAP पूर्ण झाल्यावर Done म्हणूनही खूण करतो.
[P0115|Heading 3] 3.2 — General Manager (GM)
[P0116|] ३.२ — जनरल मॅनेजर
[P0117|] The GM is the verifier. The GM logs in twice a week (typically Saturday afternoon and Monday morning). On Saturday/Monday, the GM runs the weekly audit — reviews the seven daily audits from the past week, conducts spot checks, scores the weekly-only checkpoints, and submits the weekly report to the Owner. The GM also verifies CAPs that the SM has marked Done.
[P0118|] जीएम पडताळणी करणारा. जीएम आठवड्यातून दोनदा लॉग इन करते (साधारणपणे शनिवारी दुपारी आणि सोमवारी सकाळी). शनि/सोमवारी जीएम साप्ताहिक ऑडिट चालवते — मागच्या आठवड्याची सात दैनंदिन ऑडिट पुनरावलोकन करते, स्पॉट चेक करते, साप्ताहिक-केवळ तपासणी बिंदू स्कोअर करते, आणि साप्ताहिक अहवाल मालकाला सादर करते. SM ने Done म्हणून खूण केलेल्या CAP जीएम पडताळते.
[P0119|Heading 3] 3.3 — Owner (Sagar)
[P0120|] ३.३ — मालक (सागर)
[P0121|] The Owner is the strategic user. The Owner logs in approximately weekly — Sunday morning is the typical time. The Owner reads the weekly report submitted by the GM, conducts a monthly audit on the first Sunday of each month, reviews trend dashboards, and responds to escalations. The Owner has full read-and-write access to everything in the system.
[P0122|] मालक हा सामरिक वापरकर्ता. मालक साधारणपणे साप्ताहिक लॉग इन करतो — रविवारी सकाळी सामान्य वेळ. मालक जीएमने सादर केलेला साप्ताहिक अहवाल वाचतो, दर महिन्याच्या पहिल्या रविवारी मासिक ऑडिट करतो, कल डॅशबोर्ड पुनरावलोकन करतो, आणि एस्केलेशनला प्रतिसाद देतो. मालकाला सिस्टममधल्या सर्व गोष्टींना पूर्ण वाचन-लेखन प्रवेश आहे.
[P0123|Heading 3] 3.4 — CRO (Not a logged-in user)
[P0124|] ३.४ — सीआरओ (लॉग-इन वापरकर्ता नाही)
[P0125|] CROs do not log into the app. CRO names exist in the system as a dropdown list maintained by the Store Manager (Settings → Manage CROs). When an audit Fail is logged that involves a specific CRO, the SM selects the CRO from the dropdown. The CRO never sees the app; if the CRO needs to know about a Fail, the SM tells the CRO in person.
[P0126|] सीआरओ अॅपमध्ये लॉग इन करत नाहीत. सीआरओ नावे स्टोअर मॅनेजरने सांभाळलेल्या ड्रॉपडाउन यादी म्हणून सिस्टममध्ये अस्तित्वात आहेत (सेटिंग्ज → सीआरओ व्यवस्थापन). विशिष्ट सीआरओचा समावेश असलेला ऑडिट नापास नोंदवला की SM ड्रॉपडाउनमधून सीआरओ निवडतो. सीआरओ अॅप कधीही पाहत नाही; नापासाबद्दल सीआरओला सांगायचे झाले तर SM सीआरओला प्रत्यक्ष सांगतो.

[P0133|Heading 2] Audit immutability rule
[P0134|] ऑडिट अपरिवर्तनीयता नियम
[P0135|] Once a daily, weekly, or monthly audit is submitted, it cannot be edited. Not by the auditor, not by the GM, not by the Owner. This is a deliberate rule taken directly from Workbook Section 1.3 — an editable audit is not an audit. If a mistake is discovered after submission, the correct response is to file a new audit referencing the old one and explaining the correction, never to edit the old audit. The Owner alone has the power to HIDE an audit (mark it as superseded), but even hidden audits remain in the database and in the audit_log.
[P0136|] दैनंदिन, साप्ताहिक, किंवा मासिक ऑडिट सादर झाल्यावर ती संपादित करता येत नाही. ऑडिटरने नाही, जीएमने नाही, मालकाने नाही. हा पुस्तिकेच्या विभाग १.३ मधून थेट घेतलेला जाणीवपूर्वक नियम — संपादनयोग्य ऑडिट ऑडिट नाही. सादरीकरणानंतर चूक सापडली तर योग्य प्रतिसाद म्हणजे जुन्याचा संदर्भ देणारी आणि सुधारणा स्पष्ट करणारी नवीन ऑडिट दाखल करणे, जुनी ऑडिट कधीही संपादित न करणे. फक्त मालकाला ऑडिट लपवण्याची शक्ती (अधिक्रमित म्हणून खूण करणे), पण लपवलेल्या ऑडिटही डेटाबेस आणि audit_log मध्ये राहतात.
[P0138|Heading 1] Section 4 — Complete Data Model
[P0139|] विभाग ४ — संपूर्ण डेटा मॉडेल
[P0140|Heading 2] How to read this section
[P0141|] हा विभाग कसा वाचायचा
[P0142|] The data model is the foundation. Every screen reads or writes data; if the data model is wrong, every screen built on top of it will be wrong. Each table below has: a name, a one-line purpose, every field with its type and constraints, the relationships to other tables, and worked example rows. Field types use SQLite types for the local DB; Firestore stores the same data as documents in collections of the same names.
[P0143|] डेटा मॉडेल हे पाया आहे. प्रत्येक स्क्रीन डेटा वाचतो किंवा लिहितो; डेटा मॉडेल चुकीचे असेल तर त्यावर बांधलेला प्रत्येक स्क्रीन चुकीचा असेल. खालच्या प्रत्येक टेबलला आहे: नाव, एका-ओळीचा हेतू, प्रत्येक क्षेत्र त्याच्या प्रकार व मर्यादांसह, इतर टेबलांशी संबंध, आणि उदाहरण ओळी. क्षेत्र प्रकार लोकल DB साठी SQLite प्रकार वापरतात; Firestore त्याच नावांच्या कलेक्शनमध्ये दस्तऐवज म्हणून तोच डेटा साठवतो.

[P0852|Heading 1] Section 6 — Score Calculation Logic
[P0853|] विभाग ६ — गुण मोजणी तर्क
[P0854|Heading 2] Why this section exists
[P0855|] हा विभाग का
[P0856|] This is the most error-prone area in any audit app. Get the math wrong by even 0.1 points and the audit programme loses credibility — auditors will see a Pass when the workbook says Fail, or a Fair band when the math gave Good. This section spells out every calculation Claude Code must implement, with worked examples that the app must reproduce exactly. The simulated audits in Workbook Day 5 Sections 5.1 and 5.2 serve as the canonical test cases — if your code produces a different answer from the workbook, your code is wrong, not the workbook.
[P0857|] कोणत्याही ऑडिट अॅपमधले सर्वात त्रुटी-प्रवण क्षेत्र हे आहे. गणित ०.१ गुणानेही चुकले — ऑडिट कार्यक्रमाची विश्वासार्हता जाते — पुस्तिका नापास म्हणते तेव्हा ऑडिटर पास पाहतात, किंवा गणिताने चांगले दिले तरी बरे पट्टी. हा विभाग क्लॉड कोडने अंमलात आणायची प्रत्येक गणना स्पष्ट करतो, अॅपने अचूक पुनरुत्पादन करायच्या उदाहरणांसह. पुस्तिका दिवस ५ विभाग ५.१ आणि ५.२ मधल्या अनुकरण ऑडिट अधिकृत चाचणी प्रकरणे — तुमचा कोड पुस्तिकेपेक्षा वेगळे उत्तर देत असेल, तुमचा कोड चुकीचा, पुस्तिका नाही.
[P0858|Heading 2] 6.1 — Daily audit score formula
[P0859|] ६.१ — दैनंदिन ऑडिट गुण सूत्र
[P0860|] // Pseudocode — implement exactly this
[P0861|] computeDailyScore(audit_id):
[P0862|]   results = SELECT * FROM audit_results WHERE audit_id = audit_id
[P0863|]   raw_score = 0
[P0864|]   max_score = 0
[P0865|]   pass_count = 0; fail_count = 0; na_count = 0
[P0867|]   for each r in results:
[P0868|]     cp = SELECT * FROM checkpoints WHERE id = r.checkpoint_id
[P0870|]     if r.result == 'P':
[P0871|]       raw_score  += cp.weight
[P0872|]       max_score  += cp.weight
[P0873|]       pass_count += 1
[P0874|]     elif r.result == 'F':
[P0875|]       raw_score  += 0
[P0876|]       max_score  += cp.weight
[P0877|]       fail_count += 1
[P0878|]     elif r.result == 'NA':
[P0879|]       // NA excluded from BOTH numerator and denominator
[P0880|]       na_count   += 1
[P0881|]       // do not touch raw_score or max_score
[P0883|]   compliance_pct = round(raw_score / max_score * 100, 1)  // 1 decimal
[P0884|]   band           = bandFromCompliance(compliance_pct)
[P0886|]   UPDATE audits SET raw_score, max_score, compliance_pct, band,
[P0887|]     pass_count, fail_count, na_count WHERE id = audit_id
[P0888|Heading 3] 6.2 — Compliance band function
[P0889|] ६.२ — अनुपालन पट्टी कार्य
[P0890|] bandFromCompliance(pct):
[P0891|]   if pct >= 95.0:   return 'excellent'
[P0892|]   if pct >= 90.0:   return 'good'
[P0893|]   if pct >= 85.0:   return 'fair'
[P0894|]   if pct >= 80.0:   return 'poor'
[P0895|]   return 'critical'
[P0896|Heading 2] 6.3 — Worked example: Workbook Day 5 Section 5.1
[P0897|] ६.३ — उदाहरण: पुस्तिका दिवस ५ विभाग ५.१
[P0898|] The simulated daily audit in the Workbook produced 90.0% (Good, just barely). The app MUST reproduce this exactly. If you give the app the same 12 observations and 56 implied passes, it must compute 81 / 90 = 90.0% Good. Test this every time score logic changes.
[P0899|] पुस्तिकेतल्या अनुकरण दैनंदिन ऑडिटने ९०.०% (काठावर चांगले) दिले. अॅपने हे अचूक पुनरुत्पादन करावे. अॅपला त्याच १२ निरीक्षणे आणि ५६ गृहीत पास दिल्यास, ते ८१ / ९० = ९०.०% चांगले मोजले पाहिजे. गुण तर्क बदलला की दर वेळी हे तपासा.
[P0901|] compliance_pct = round(81 / 90 * 100, 1) = 90.0
[P0902|] band = 'good'  // 90.0 >= 90.0
[P0903|Heading 2] 6.4 — Daily audit with NAs
[P0904|] ६.४ — NA सह दैनंदिन ऑडिट
[P0905|] Example: 5 checkpoints marked NA, all weighted 2 (e.g. it was a Cash holiday — no GRN, no service intake, no high-value movement). Sum of NA weights = 10. So max_score is 90 − 10 = 80, not 90.
[P0906|] उदाहरण: ५ तपासणी बिंदू NA, सर्व वजन २ (उदा. रोख सुट्टी — GRN नाही, सर्व्हिस इनटेक नाही, उच्च-मूल्य हालचाल नाही). NA वजनांची बेरीज = १०. म्हणून max_score ९० नसून ९० − १० = ८०.
[P0907|] // Suppose results: 58 P (weighted), 5 F (weighted), 5 NA (weighted)
[P0908|] // Pass weighted points: 58 × avg(weight) = let's say 70
[P0909|] // Fail weighted points: 5 × avg(weight) = let's say 10
[P0910|] // raw_score = 70  (only passes count toward numerator)
[P0911|] // max_score = 70 + 10 = 80  (NAs excluded from denominator)
[P0912|] // compliance_pct = 70/80 * 100 = 87.5  ->  band = 'fair'
[P0913|Heading 2] 6.5 — Weekly audit score formula (Phase 2)
[P0914|] ६.५ — साप्ताहिक ऑडिट गुण सूत्र (टप्पा २)
[P0915|] computeWeeklyScore(weekly_audit_id):
[P0916|]   // 1. Daily-audit-average contribution (out of 68)
[P0917|]   week_dates = 7 dates of the week being audited
[P0918|]   daily_pcts = []
[P0919|]   for each date in week_dates:
[P0920|]     daily = SELECT * FROM audits WHERE audit_type='daily' AND audit_date=date
[P0921|]     if daily exists AND status='submitted':
[P0922|]       daily_pcts.push(daily.compliance_pct)
[P0923|]     else:
[P0924|]       daily_pcts.push(0.0)  // missing day = 0%
[P0925|]   avg_daily = sum(daily_pcts) / 7
[P0926|]   daily_contribution = round(avg_daily / 100 * 68, 1)
[P0928|]   // 2. Weekly-only checkpoints (max 56 weighted)
[P0929|]   weekly_results = SELECT * FROM audit_results WHERE audit_id = weekly_audit_id
[P0930|]   weekly_raw = sum of weighted_points where result='P'
[P0931|]   weekly_max = sum of cp.weight where result IN ('P', 'F')  // NA excluded
[P0933|]   // 3. Combine
[P0934|]   total_raw = daily_contribution + weekly_raw
[P0935|]   total_max = 68 + weekly_max  // 124 if no weekly NAs
[P0936|]   compliance_pct = round(total_raw / total_max * 100, 1)
[P0937|Heading 2] 6.6 — Worked example: Workbook Day 5 Section 5.2
[P0938|] ६.६ — उदाहरण: पुस्तिका दिवस ५ विभाग ५.२
[P0939|] Daily percentages: 92.2, 91.1, 90.0, 88.8, 93.3, 89.7, 91.4. Sum = 636.5. Average = 90.93%. Daily contribution = 90.93 × 0.68 = 61.8 (rounded to 1 decimal).
[P0940|] दैनंदिन टक्केवारी: ९२.२, ९१.१, ९०.०, ८८.८, ९३.३, ८९.७, ९१.४. बेरीज = ६३६.५. सरासरी = ९०.९३%. दैनंदिन योगदान = ९०.९३ × ०.६८ = ६१.८ (एक दशांशात गोलाकार).
[P0941|] Weekly-only: Operations 7/10, Cash 10/16, R&S 4/6, Inventory 22/24. Sum: 43/56. Total: 61.8 + 43 = 104.8 / 124 = 84.5%. Band: Poor.
[P0942|] साप्ताहिक-केवळ: ऑपरेशन्स ७/१०, रोख १०/१६, R&S ४/६, स्टॉक २२/२४. बेरीज: ४३/५६. एकूण: ६१.८ + ४३ = १०४.८ / १२४ = ८४.५%. पट्टी: वाईट.
[P0943|Heading 2] 6.7 — Cumulative weekly cash variance check (CW.7)
[P0944|] ६.७ — एकत्रित साप्ताहिक रोख तफावत तपासणी (CW.७)
[P0945|] computeCumulativeWeeklyVariance(week_dates):
[P0946|]   variances = []  // signed: + over, - short
[P0947|]   for each date in week_dates:
[P0948|]     daily = SELECT * FROM audits WHERE audit_type='daily' AND audit_date=date
[P0949|]     // Stored as separate field on audit (parsed from cash result finding text
[P0950|]     //   OR captured explicitly during S7 cash checkpoint)
[P0951|]     if daily:
[P0952|]       variances.push(daily.cash_variance_rupees)
[P0953|]   cumulative = sum(variances)
[P0954|]   return |cumulative|  // absolute value for comparison
[P0956|] CW.7 result:
[P0957|]   if |cumulative| <= 200: Pass
[P0958|]   else: Fail (with cumulative value shown in finding)
[P0959|] To support CW.7, the cash checkpoint 6.5 in the daily audit captures an additional field cash_variance_rupees (positive if over, negative if short). This is stored on the audit row directly. The weekly audit reads these 7 numbers and sums.
[P0960|] CW.७ साठी, दैनंदिन ऑडिटमधला रोख तपासणी बिंदू ६.५ एक अतिरिक्त फील्ड cash_variance_rupees पकडतो (जास्त असेल पॉझिटिव्ह, कमी असेल निगेटिव्ह). हा थेट audit ओळीवर साठवला जातो. साप्ताहिक ऑडिट या ७ संख्या वाचते आणि बेरीज करते.

[P0963|] विभाग ७ — एस्केलेशन नियम — निर्णय इंजिन
[P0964|Heading 2] Where the engine runs
[P0965|] इंजिन कुठे चालते
[P0966|] After every audit submission (S10 → submit), and after certain CAP state changes, the escalation engine evaluates the seven mandatory triggers from Workbook Day 4 Section 4.6. [P0968|Heading 2] The 7 triggers as code logic
[P0969|] ७ ट्रिगर कोड तर्क म्हणून
[P0970|] runEscalationEngine(audit_id):
[P0971|]   a = SELECT * FROM audits WHERE id = audit_id
[P0973|]   // Trigger 1: Daily Critical band (< 80%)
[P0974|]   if a.audit_type == 'daily' AND a.band == 'critical':
[P0975|]     cash_cause = any 6.x checkpoint failed
[P0976|]     inv_cause  = any 7.x checkpoint failed
[P0977|]     raise(trigger=1, to=GM, urgency='same_night',
[P0978|]           via='whatsapp' if (cash_cause OR inv_cause) else 'in_app')
[P0979|]     if cash_cause OR inv_cause:
[P0980|]       raise(trigger=1, to=Owner, urgency='same_night', via='whatsapp')
[P0982|]   // Trigger 2: Same checkpoint failing 5+ days in a week
[P0983|]   // (evaluated only when weekly audit is submitted)
[P0984|]   if a.audit_type == 'weekly':
[P0985|]     for each cp where same checkpoint failed >= 5 of last 7 daily audits:
[P0986|]       raise(trigger=2, to=GM, urgency='next_audit', via='in_app')
[P0988|]   // Trigger 3: Cash variance > ₹500 single day
[P0989|]   if a.audit_type == 'daily' AND abs(a.cash_variance_rupees) > 500:
[P0990|]     raise(trigger=3, to=GM, urgency='same_day', via='whatsapp')
[P0991|]     // Check yesterday — if also > 500, escalate to Owner
[P0992|]     yest = SELECT FROM audits WHERE audit_date=a.audit_date-1day
[P0993|]     if yest AND abs(yest.cash_variance_rupees) > 500:
[P0994|]       raise(trigger=3, to=Owner, urgency='immediate', via='whatsapp')
[P0996|]   // Trigger 4: Inventory variance > 2% of stock value
[P0997|]   if a.audit_type == 'weekly' AND a.inventory_variance_pct > 2.0:
[P0998|]     raise(trigger=4, to=Owner, urgency='same_day', via='whatsapp')
[P1000|]   // Trigger 5: Theft / security / legal — manual flag from finding
[P1001|]   for each result in audit_results:
[P1002|]     if result.flag_security_concern == 1:
[P1003|]       raise(trigger=5, to=Owner, urgency='immediate', via='whatsapp')
[P1005|]   // Trigger 6: Customer complaint not store-resolvable — manual
[P1006|]   // (raised from CAP detail or audit notes by user action, not auto)
[P1008|]   // Trigger 7: Declining trend 3+ consecutive weeks
[P1009|]   if a.audit_type == 'weekly':
[P1010|]     last4 = SELECT compliance_pct FROM audits WHERE audit_type='weekly'
[P1011|]             ORDER BY audit_date DESC LIMIT 4
[P1012|]     if len(last4) >= 3 AND last4[0] < last4[1] < last4[2]:
[P1013|]       raise(trigger=7, to=Owner, urgency='same_day', via='in_app')

[P1880|] keystore फाइल कधीही कमिट करू नका. पासवर्ड-संरक्षित, वेगळी साठवा.

[P2048|Heading 1] Section 17 — Recovery Patterns — When Claude Code Goes Off-Track
[P2049|] विभाग १७ — पुनर्प्राप्ती पॅटर्न — क्लॉड कोड भरकटला तर
[P2050|Heading 2] Why this section exists
[P2051|] हा विभाग का
[P2052|] Claude Code is excellent but not infallible. Over a 13-week build, it will at some point: suggest swapping a locked library, add a feature you did not ask for, write code that doesn't match the Spec, or get stuck in a loop fixing one bug while introducing another. This section is the playbook for those moments. The single most important recovery skill is knowing when to roll back to the last known-good commit and try again, rather than trying to patch a broken state.
[P2053|] क्लॉड कोड उत्कृष्ट पण निर्दोष नाही. १३-आठवड्यांच्या बांधणीत, कधीतरी ते: लॉक केलेली लायब्ररी बदलण्याचे सुचवेल, तुम्ही न मागितलेले फीचर जोडेल, तपशीलाशी न जुळणारा कोड लिहेल, किंवा एक बग दुरुस्त करताना दुसरा आणणाऱ्या लूपमध्ये अडकेल. त्या क्षणांसाठी हा विभाग म्हणजे playbook आहे. एकमेव सर्वात महत्त्वाचे पुनर्प्राप्ती कौशल्य म्हणजे तुटलेली स्थिती patch करण्याचा प्रयत्न करण्याऐवजी कधी मागच्या ज्ञात-चांगल्या कमिटवर परत जायचे ते जाणणे.
[P2054|Heading 2] 17.1 — Anti-pattern detection — what to watch for
[P2055|] १७.१ — विरुद्ध-पॅटर्न शोध — कशावर लक्ष ठेवायचे
[P2056|List Paragraph] Claude Code says "I'll just use Provider instead of Riverpod — it's simpler." → REJECT. Tech stack is locked. Reply: "Stay with Riverpod per Spec Section 2.2."
[P2057|] क्लॉड कोड म्हणतो "मी फक्त Riverpod ऐवजी Provider वापरतो — सोपे आहे." → नकार द्या. Tech stack लॉक. उत्तर द्या: "Spec Section 2.2 नुसार Riverpod वर रहा."
[P2058|List Paragraph] Claude Code adds a new column to a table without updating the Spec or migration. → REJECT. Reply: "Add the column to the Spec Section 4 first. Show me the diff. Then write the migration."
[P2059|] क्लॉड कोड Spec किंवा migration न अद्यतनित करता तक्त्यात नवीन स्तंभ जोडतो. → नकार. उत्तर: "आधी Spec Section 4 ला स्तंभ जोडा. diff दाखवा. मग migration लिहा."
[P2060|List Paragraph] Claude Code creates a screen not in Spec Section 5. → REJECT. Reply: "That screen is not in the Spec. If you think it should be, add it to docs/v2-wishlist.md. Continue with the current Phase scope."
[P2061|] क्लॉड कोड Spec Section 5 मध्ये नसलेला स्क्रीन तयार करतो. → नकार. उत्तर: "तो स्क्रीन Spec मध्ये नाही. असावा वाटले — docs/v2-wishlist.md ला जोडा. सध्याच्या टप्पा व्याप्तीत राहा."
[P2062|List Paragraph] Claude Code says "the previous code was wrong, let me rewrite everything." → PAUSE. Reply: "Don't rewrite. Show me which file is wrong and explain why. We'll fix the one file."
[P2063|] क्लॉड कोड म्हणतो "मागचा कोड चुकीचा होता, मी सर्व पुन्हा लिहितो." → थांबा. उत्तर: "पुन्हा लिहू नका. कोणती फाइल चुकीची आणि का स्पष्ट करा. आपण एकच फाइल दुरुस्त करू."
[P2064|List Paragraph] Claude Code makes multi-file changes without committing in between. → STOP. Reply: "Commit what you have first. Show me the diff. Then continue."
[P2065|] क्लॉड कोड मध्ये कमिट न करता बहु-फाइल बदल करते. → थांबा. उत्तर: "आधी जे आहे ते कमिट करा. diff दाखवा. मग पुढे."
[P2066|List Paragraph] Claude Code's score engine produces 89.99 or 90.01 instead of 90.0. → STOP. Reply: "The math should produce 90.0 exactly. Re-read Spec Section 6 and find the rounding bug."
[P2067|] क्लॉड कोडचे गुण इंजिन ९०.० ऐवजी ८९.९९ किंवा ९०.०१ तयार करते. → थांबा. उत्तर: "गणित अचूक ९०.० तयार करावे. Spec Section 6 पुन्हा वाचा आणि rounding बग शोधा."
[P2068|List Paragraph] Claude Code says "I'll add Firebase Auth — it's better than custom PIN." → REJECT. Reply: "PIN auth is locked decision #2 in Spec Section 1. Do not change."
[P2069|] क्लॉड कोड म्हणते "मी Firebase Auth जोडतो — कस्टम PIN पेक्षा चांगले." → नकार. उत्तर: "PIN auth Spec Section 1 मध्ये निर्णय #२ लॉक. बदलू नका."
[P2070|Heading 2] 17.2 — Git rollback procedures
[P2071|] १७.२ — Git rollback प्रक्रिया
[P2072|Heading 3] Soft rollback — undo last commit, keep changes
[P2073|] मऊ rollback — मागचा कमिट पूर्ववत, बदल ठेवा
[P2074|] git reset --soft HEAD~1
[P2075|List Paragraph] Use when: the last commit message is wrong, or you want to bundle the last commit's changes with new work.
[P2076|] वापर: मागच्या कमिटचा संदेश चुकीचा, किंवा मागच्या कमिटचे बदल नवीन कामासोबत बंडल करायचे.
[P2077|Heading 3] Hard rollback — discard last commit and its changes
[P2078|] कठोर rollback — मागचा कमिट आणि त्याचे बदल टाकून
[P2079|] git reset --hard HEAD~1
[P2080|List Paragraph] Use when: Claude Code wrote a wrong implementation and you want to start that change over.
[P2081|] वापर: क्लॉड कोडने चुकीची अंमलबजावणी लिहिली आणि तो बदल नव्याने सुरू करायचा.
[P2082|List Paragraph] WARNING: uncommitted changes are lost. Stash first if needed: `git stash`.
[P2083|] इशारा: कमिट न केलेले बदल गमावले जातात. गरज पडल्यास आधी stash करा: `git stash`.
[P2084|Heading 3] Rollback to a specific known-good commit
[P2085|] विशिष्ट ज्ञात-चांगल्या कमिटवर rollback
[P2086|] git log --oneline                  # find the commit hash
[P2087|] git reset --hard <commit-hash>     # roll back to that point
[P2088|List Paragraph] Use when: multiple commits are broken and you need to go back further.
[P2089|] वापर: अनेक कमिट तुटलेले आणि आणखी मागे जायचे.
[P2090|Heading 3] Branch-and-explore — try without breaking main
[P2091|] शाखा-व-शोध — main न मोडता प्रयत्न
[P2092|] git checkout -b experiment/<name>  # create a new branch
[P2093|] # ... try changes ...
[P2094|] git checkout main                  # return to main
[P2095|] git branch -D experiment/<name>    # delete experiment if bad
[P2096|List Paragraph] Use when: you want to try a risky change without committing to it.
[P2097|] वापर: कमिट न करता धोकादायक बदल वापरून पाहायचा.
[P2098|Heading 2] 17.3 — The reset prompt — when to start a session fresh
[P2099|] १७.३ — रीसेट प्रॉम्प्ट — सत्र नव्याने कधी सुरू करायचे
[P2100|] If Claude Code has clearly lost the plot in a session — repeating the same mistake, making contradictory claims, or hallucinating about the codebase — close the session and start a new one. Paste the Session-Start Prompt again. Most session drift recovers from a fresh context.
[P2101|] क्लॉड कोडने सत्रात स्पष्टपणे कथानक गमावले — तीच चूक पुनरावृत्ती, परस्परविरोधी दावे, किंवा codebase बद्दल hallucinations — सत्र बंद करा आणि नवीन सुरू करा. सत्र-सुरुवात प्रॉम्प्ट पुन्हा पेस्ट करा. बहुतेक सत्र drift ताज्या context मधून पुनर्प्राप्त होते.
[P2102|Heading 2] 17.4 — When to escalate to a human Flutter developer
[P2103|] १७.४ — मानवी Flutter डेव्हलपरकडे कधी एस्केलेट करायचे
[P2104|List Paragraph] Claude Code has been stuck on the same bug for 3+ sessions and progress has gone backward.
[P2105|] क्लॉड कोड ३+ सत्रांसाठी त्याच बगवर अडकले आणि प्रगती मागे गेली.
[P2106|List Paragraph] A feature involves a Flutter or Firebase quirk that needs deep platform knowledge (e.g., Android background task limitations on specific OEMs).
[P2107|] फीचरमध्ये खोल प्लॅटफॉर्म ज्ञान लागणारा Flutter किंवा Firebase quirk (उदा. विशिष्ट OEM वर Android background task मर्यादा).
[P2108|List Paragraph] Sagar wants to ship faster than the 13-week phasing allows.
[P2109|] सागरला १३-आठवड्यांच्या टप्प्यांपेक्षा वेगाने शिप करायचे.
[P2110|List Paragraph] Approach: hand the Spec + Workbook + the GitHub repo to a freelance Flutter developer. They start from the same documents. No knowledge is lost in handover.
[P2111|] दृष्टिकोन: Spec + Workbook + GitHub repo फ्रीलान्स Flutter डेव्हलपरला सोपवा. ते त्याच कागदपत्रांवरून सुरू करतात. हस्तांतरणात ज्ञान गमावले जात नाही.
